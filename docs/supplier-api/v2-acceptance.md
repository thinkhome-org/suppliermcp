## Published RC3 and the clean catalogue

[RC3](https://github.com/thinkhome-org/suppliermcp/releases/tag/v2.0.0-rc.3) passed CI, CodeQL and the published-digest smoke/rollback job. The SHA-256 checksums of the downloaded wheel, native and portable plugin archives, and image reference were verified locally. RC2's release job stopped at a version mismatch before publishing artifacts; RC3 derives both plugin versions from package metadata.

The temporary HTTPS endpoint was switched to the verified RC3 wheel. On this endpoint a Keycloak-issued personal token completed an eD invoice-list read (HTTP 200); the ordinary client received HTTP 403 for the same read. An actual Codex CLI session completed eD PRIVATE transportation and eD PUBLIC invoice-list MCP calls. The catalogue library also exercised ELINKX PUBLIC/PRIVATE and an i6ws category export using their declared protocol profiles.

On the signed-in personal ChatGPT website, the operator created the cloud plugin and authenticated to its temporary OAuth realm. The first test window closed before the separate **Connect** step. After explicit authorization, the temporary endpoints were reopened, Connect was confirmed and a fresh login completed. **Try in chat** opened the ordinary **Chat** composer. At 18:13:27 and 18:13:28 UTC on 2026-11-06, the released RC3 service recorded successful `read_operation` calls from the ChatGPT client for `ed_private.getTransportationList` and `ed_public.getInvoiceList`. The visible chat response reported success for both. The protected receipts contain the operation IDs and success only, with no supplier values. Both public DNS records, the tunnel, the disposable login service and its credentials were removed after the test. The permanent local Codex service still returned healthy after cleanup. Production Portainer v2 cutover remains pending access to its Docker environment. The v1 manifest retained its original bytes on main; the v2 manifest uses a separate filename and candidate origin alias.

A separate v2 database was populated through the projected adapters. Verified retained eD PUBLIC and 100MEGA source artifacts were re-parsed; the eD PRIVATE baseline and stock export were fetched from the account. At revision 11 the database contained 157,824 active products. All rows in the complete price-ordered listing matched an independent SQL calculation. [Search, index rebuild and latency evidence](v2-search-validation.md).

A persistent, loopback-only RC3 Docker installation was then enabled in the operator's regular Codex configuration under the MCP name `supdb_v2`. After an MCP container restart, the installed CLI searched the live catalogue and returned an eD invoice-list response through that named connection. A separate catalogue-only client was denied the invoice operation; an anonymous request was rejected. The clean database and index each contained 157,824 products at the check. The API, worker, database and index have persisted storage/restart configuration; the check did not reboot the host. This installation is independent of the disposable web-test tunnel.

## Durable Portainer deployment, 6 November 2026

Portainer environment 3 started the RC3 application in stack 25 (`supdb-green`) and its dedicated Keycloak realm in stack 26 (`supdb-login`). The database migration exited successfully. At 20:24 UTC the green origin passed readiness and rejected anonymous and invalid MCP requests. The existing v1 origin retained its separate route and passed readiness. The durable [MCP endpoint](https://supdb.thinkhome.org/mcp) and [SupDB realm discovery](https://supdb-login.thinkhome.org/realms/supdb/.well-known/openid-configuration) passed public HTTPS checks. The public login host returned 404 for the administrative route.

Authorization-code login with PKCE succeeded for the two personal registrations and the ordinary registration. All three discovered nine MCP tools and read the eD transportation list. Both personal registrations read the invoice list; the ordinary registration was denied. These checks exercised the deployed service using real tokens. Supplier rows, login details and private receipts stay outside the repository.

The operator also connected the permanent SupDB plugin in the signed-in personal ChatGPT web interface. In ordinary Chat, the new plugin successfully called `ed_private.getTransportationList` and `ed_public.getInvoiceList`. The chat reported both outcomes without displaying supplier values.

After a restart of the green MCP container, authenticated catalogue status and search both returned HTTP 200. On the same Portainer environment, a disposable v1 database containing a synthetic SKU exercised the rollback procedure. RC3 refused the populated v1 database, a PostgreSQL backup restored into separate storage, and the pinned v1 API found the restored SKU through authenticated MCP at 20:34 UTC. The disposable stack was removed. These receipts apply to RC3.

## 100MEGA evening windows, 6 November 2026

All 57 previously window-blocked operation IDs completed at their minimum required scope. The 20:00 UTC cohort returned 34 nonempty and 21 valid empty responses (55/55); at 21:00 UTC both targeted stock-quantity operations returned business fields (2/2). The four additional X-HOG dual-scope checks returned valid empty responses. Their IDs overlap the first cohort. Each row in the [per-operation evidence](v2-read-probes.json) retains its earlier window denial and the actual observation time. A nonempty first page proves the tested read, not an exhaustive catalogue download.

Across the 326 reviewed reads, 221 returned business fields and 99 returned valid empty responses (320/326). The remaining six are the three GetXCompany denials, two X-ASM-StiRelation delta SQL errors and the missing genuine order for GetStatus.
